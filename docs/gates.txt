Each flag below is a gate: it asserts on the live runtime (or the shipped data) and exits
non-zero if the behaviour drifts. `--gates` runs the whole list, one process per flag, and says
which **mode** each one ran in:

```text
flag                   runs       result verdict
--controls             headless   pass   --- controls check passed ---
--live-check           window     pass   --- live check passed ---
```

* **headless** — the flag returns before `App::new()`: it parsed the level, ran the runtime, and
  never created a window, a camera or a menu. Most gates are this, and this column is how you can
  tell without reading `main`.
* **window** — the flag needed the running game, so it printed `mode: window, <screen>` first.
  Nine gates are windowed: `--live-check`, `--goal`, `--save-live`, `--save-slots`, `--use-live`,
  `--ai-live`, `--force-live`, `--force-grant` and `--tour-live`. Each names the screen it ran
  against and prints a verdict, and the sweep counts a window row with no verdict as a failure.

Two flags exist to keep runs finite: `--exit-after N` (or `BK_EXIT_FRAMES=N`) quits after N frames
whatever is on screen, and `--gates` passes it to every child. A gate that forgets to quit then
ends without a verdict instead of sitting on the main menu forever — which is what five flags that
do not exist in this binary used to do, because a hand-written flag list had invented them.

`BK_HEADLESS=1` runs with no window, so the nine windowed gates cannot run: the sweep reports them
as **skipped**, never as passes (`gates: 0 of 61 failed, 9 skipped`). `BK_SKIP_WINDOW=1` skips only
`--live-check` and says so. The headless mode exists because `--live-check` needs a display that is
actually presenting: with no focused desktop the app sits in presentation after its setup output and
never reaches the hundredth frame its verdict is gated on, so the sweep would hang instead of
finishing. Everything else is headless and unaffected.
